# 36 — Release pipeline, licenses, checksums

## Title
Release pipeline, licenses, and checksums

## Summary
Build a tag-triggered GitHub Actions release workflow that produces reproducible `--locked`
binaries for macOS and Linux (x86_64 + aarch64 where feasible), attaches SHA-256 checksums
and build provenance, ships license files + man page + completions, and drafts release
notes (DESIGN §10.6).

## Context
Trustworthy distribution is part of the security model: users must be able to verify what
they download (DESIGN §10.6). Signing keys are generated by the user, not the agent
(project rule); the pipeline provides everything up to signing.

## Scope
- In: `.github/workflows/release.yml`, license files (`LICENSE-MIT`, `LICENSE-APACHE` per
  ADR-006), packaging (binary + man page + completions + licenses), checksums, provenance,
  draft notes.
- Out: pushing to crates.io / Homebrew tap (v2 idea unless the user wants it; document as
  optional), actual key generation/signing (user-performed handoff).

## Detailed Requirements
1. Trigger on a version tag (`v*`). Build with `cargo build --locked --release` per target:
   `x86_64-apple-darwin`, `aarch64-apple-darwin`, `x86_64-unknown-linux-gnu` (and
   `aarch64-unknown-linux-gnu` if a runner/cross is available; else document as follow-up).
   Consider `-musl` for a static Linux binary (evaluate; note glibc vs musl trade-offs for
   the sandbox syscalls).
2. Package per target: the `dryrun` binary, `dryrun.1` (34), completion scripts (34),
   `LICENSE-MIT`, `LICENSE-APACHE`, `README.md`. Produce a tarball + a `SHA256SUMS` file.
3. Provenance: enable GitHub Actions build provenance/attestation (SLSA-style) for the
   artifacts where supported; document how users verify.
4. Reproducibility: `--locked`, pinned toolchain, `strip`; document the exact build command
   so a third party can reproduce and compare checksums.
5. License files added at repo root per ADR-006 (Accepted 2026-07-11: **MIT OR Apache-2.0**;
   ship both `LICENSE-MIT` and `LICENSE-APACHE`). `Cargo.toml` `license` field matches. Fill
   the copyright holder/year from the user's confirmed identity (do not invent a name).
6. Signing handoff: the workflow prepares artifacts + checksums; **the user** generates keys
   and signs (project rule: agents do not generate secrets/keys). Document the exact signing
   + verification steps as a handoff in the release notes/`SECURITY.md`.
7. Draft (not publish) the GitHub Release with generated notes; a human publishes.
8. Panic strategy finalization: confirm the release profile's panic setting does not skip
   sandbox teardown (coordinate with 26); add a test/assertion if `panic = "abort"` is
   chosen.

## Acceptance Criteria
- A tag build produces per-target tarballs with binary + man + completions + licenses +
  `SHA256SUMS`.
- Checksums verify; provenance/attestation is attached where supported.
- License files present and consistent with `Cargo.toml` and ADR-006 (once confirmed).
- The release is drafted, not auto-published; signing steps are documented as a user
  handoff (no keys generated by CI/agent).
- License files (`LICENSE-MIT`, `LICENSE-APACHE`) are present and consistent with
  `Cargo.toml` (ADR-006 Accepted: MIT OR Apache-2.0).

## Validation
- A dry-run tag (e.g. `v0.0.0-rc`) on a branch produces the artifacts; verify checksums and
  contents; confirm the release is a draft.

## Dependencies
32 (deny/locked), 33 (CI), 34 (man/completions), 38 (AppArmor profile to package). ADR-006
license confirmed (2026-07-11, no longer a blocker).

## Non-goals
No crates.io/Homebrew publishing in v1 (optional/v2); no key generation or signing by the
agent.
